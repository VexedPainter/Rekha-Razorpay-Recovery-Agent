# Adapter compatibility and trust tiers

What each host adapter for the Native Agent Gate (E18) actually supports
today, and what `trust_tier` it honestly reports per surface. Generated by
reading the real adapter code (`belay/hooks/*_adapter.py`), not asserted
from a roadmap -- if this table and the code disagree, the code is right
and this file is stale.

## Trust tier definitions

| Tier | Meaning |
|---|---|
| `T1` | A pinned-version, end-to-end conformance suite has actually run against a real installed binary of this host and passed, proving a denied action's side effect genuinely never happens (see [ADR 0020](adr/0020-extended-requirement-catalog.md)'s `TRUTH-004`). |
| `UNKNOWN` | No such suite exists yet for this host/surface. The gate still makes real allow/pause/deny decisions -- `UNKNOWN` is honesty about *verification*, not a claim that the surface is unprotected. |
| `T0`/`T2` | Reserved in `belay/supervisor/protocol.py`'s `TrustTier` type for future, more granular tiers (e.g. a suite that ran but found gaps). Not used by any adapter today. |

`trust_tier` is informational metadata recorded on every `HookEvent` and
into the ledger (spec §9) -- it does **not** gate the decision itself
(`belay/hooks/gate.py` never reads it). A `T1` vs `UNKNOWN` event can both
still be correctly allowed, paused, or denied; the field only answers "has
this exact combination of host and surface been end-to-end verified."

## What "wired to a live session" actually means

Only Claude Code's Bash surface has ever been exercised end-to-end: a real
`claude` CLI process, with Belay's hooks actually installed, attempting a
denied command, and the suite confirming the command's side effect never
touched disk. Codex and OpenCode's adapters correctly *transform* a real
payload shape into `HookEvent` (checked against a real installed binary's
schema/source), but no test has ever driven a live Codex or OpenCode
session through the gate and confirmed a deny actually blocked anything.
Treat both as "the plumbing is real, the seal is not" until each gets its
own equivalent of `tests/hooks/test_live_conformance.py`.

## A real bug this document caught

Before this file existed, `claude_code_adapter._trust_tier()` returned
`"T1"` for *every* Claude Code event, regardless of `surface` -- so an
Edit/Write or native MCP event's ledger entry would have recorded
`trust_tier: "T1"`, even though no conformance suite has ever run against
those surfaces. Fixed to scope `T1` to `surface == "shell"` only; see the
regression test
`tests/hooks/test_claude_code_adapter.py::test_trust_tier_is_unknown_for_non_bash_surfaces_even_though_bash_is_t1`.

## Updating this table

Whoever adds a live-conformance suite for a new host/surface combination
should update the corresponding cell in the same commit that flips
`_VERIFIED_TRUST_TIER`/adds the `T1` check -- this file is not
CI-enforced (unlike `docs/traceability.md`), so it can go stale if edited
separately from the code. Cross-check the "Trust tier definitions"
section against `belay/supervisor/protocol.py`'s `TrustTier` docstring if
in doubt.
